## 已确认的产品边界

### C01 生成式回答：已确认不纳入CueKB（2026-09-22）

CueKB是供外部系统集成的知识库与检索服务，目标是快速返回准确、可追溯且经过权限和版本校验的检索结果。是否将结果交给LLM、选择哪个LLM以及如何生成回答，均由外部系统自行决定；外部系统也可以直接使用检索结果。

不新增内置回答服务、`POST /v1/answer`、生成式模型配置或门户问答功能。现有门户继续用于知识库管理和检索验证；Embedding与Reranker继续服务于检索。M4证据状态用于描述评估结果，不替外部系统决定是否调用LLM。正式决策见`DECISIONS.md`的D19。

### C02 OIDC身份适配

- **现状与场景**：生产入口通过Bearer API Key得到`Principal`，再由PG校验知识库权限；尚无OIDC用户登录。只有需要企业单点登录或区分最终用户时才增加OIDC。
- **需要确认**：IdP名称、issuer、audience、用户/服务账号类型、门户是否直接登录；用户组与知识库角色的管理归属；离职/撤权传播时限；调用方究竟代表服务本身还是具体用户。
- **建议方案**：在鉴权入口增加独立OIDC适配器，把经验证的外部身份映射为内部`Principal`，外部身份键采用issuer与subject组合。知识库授权继续由PG管理；首版不因外部角色字符串自动获得system admin或KB权限。服务到服务调用保留API Key，两种认证路径明确区分，OIDC校验失败不得回退成其他身份。
- **实施与验收**：增加身份映射的增量迁移、令牌验证与受控密钥刷新；门户登录另行确定会话方案。明确短期令牌有效期、停用状态及最终复验策略，验证issuer/audience错误、过期、密钥轮换、禁用和撤权。不信任请求体或普通请求头声明的用户、角色或KB列表；共享服务API Key自身不能证明最终用户权限。
- **影响与依赖**：`api/dependencies.py`、`domain/models.py`、`adapters/postgres.py`、检索最终复验和门户。需先确定IdP及授权责任，OIDC本身不能替代ACL设计。

### C03 对象存储适配

- **现状与场景**：`LocalFileStorage`按内容SHA-256保存原件；Worker读取本地文件，下载接口通过`resolve()`和`FileResponse`依赖本地路径。只更换上传目标无法完成对象存储接入。
- **需要确认**：目标产品和实际接口、endpoint/bucket/区域、凭据取得方式、API/Worker网络访问、容量与单文件上限、加密密钥归属、版本保留、备份及迁移窗口。
- **建议方案**：保留本地适配器，在现有存储边界提取保存、读取/流式读取、删除能力，再实现选定产品适配器；PG保存受控存储标识及摘要，不保存临时签名URL。下载首版仍经API授权后代理，避免引入长期可转发的访问链接。
- **实施与验收**：同时修改上传、Worker读取、原文下载和清理路径；旧`source_uri`继续可读，通过可续跑迁移任务复制并核对摘要，验证完成后切换引用。验证中断重试、对象缺失、跨库同内容引用、权限拒绝、大小边界及备份恢复；不在存储迁移时自动删除旧原件。
- **影响与依赖**：`adapters/storage.py`、`api/dependencies.py`、`api/routes.py`、`worker.py`、配置及部署文档；与C08统一删除策略，跨主机扩容前完成共享原件方案。

### C04 多`scope`发布

- **现状与场景**：版本已有`scope`元数据，但数据库CHECK、`PublishRequest`和仓储发布逻辑均仅允许`default`。例如同一手册的设备A版和设备B版要同时有效，才需要多发布指针；普通元数据过滤不等于多范围发布。
- **需要确认**：scope描述型号、软件版本、项目还是其他维度；取值与版本比较规则；一个请求是否允许多个scope；未指定范围、范围重叠及缺失匹配时如何处理；是否允许回退到default。
- **建议方案**：首版使用显式、规范化scope标识，每个文档每个scope只有一个活动版本。旧请求继续明确对应default；非default请求要求显式选择，找不到时返回无匹配或要求澄清，不悄悄跨范围回退。暂不引入隐式优先级与任意条件表达式。
- **实施与验收**：在增量迁移中调整约束，并贯通请求、发布、候选过滤、PG最终复验、上下文、关系证据、原文下载与generation重建。版本是否过期须检查所有发布指针，不能因一个scope替换就清除其他scope仍引用的版本。验证双scope并存、重复命中去重、切换竞态和旧default请求兼容。
- **影响与依赖**：`schemas.py`、`adapters/postgres.py`、`adapters/knowledge.py`、generation及Worker清理逻辑、门户。scope只表达内容适用性，不作为授权机制；建议排在范围规则确认之后。

### C05 文档级ACL

- **现状与场景**：当前read/write/admin均作用于知识库，已确认D08要求不同权限范围优先拆知识库。若同一知识库必须混合普通手册和仅少数人员可见的内部文档，才考虑此项。
- **需要确认**：无法拆库的具体案例；控制read还是也控制write/admin；无文档规则时是否继承KB；用户组支持、KB管理员边界、移动文档及追加版本后的继承规则。
- **建议方案**：首版只增加文档读取限制：必须先有KB read；未设置文档限制时继承KB，有限制时再满足文档允许名单，文档规则不能扩大KB授权。规则绑定逻辑文档并覆盖其版本；KB管理和system admin边界单独明确记录。
- **实施与验收**：PG增加规则及授权修订信息；检索返回前、关系及上下文扩展、文档列表/详情、任务信息、原文和显式历史版本下载均使用统一检查。过滤后结果不足不得放宽权限；若补召回必须有界。验证标题、锚点、关系、上下文及任务元数据泄漏，覆盖查询期间撤权。
- **影响与依赖**：所有读取入口、PG仓储、`adapters/knowledge.py`、检索与后续缓存，属于跨模块权限变更。建议先完成C02的身份模型（若启用），再实现C05，最后考虑C06。

### C06 应用级检索缓存

- **现状与场景**：当前依赖中的`lru_cache`缓存的是组件实例，不是搜索结果。只有重复查询占比、模型开销和P95测量支持时，检索结果缓存才有明确收益。
- **需要确认**：目标收益、查询重复率、容量/字节上限、TTL、是否多API副本及敏感查询保存要求。TTL只控制回收，不允许成为撤权延迟窗口。
- **建议方案**：首版采用可关闭的进程内有界LRU与TTL，不新增Redis；缓存候选ID和必要排序信息，命中后重新从PG获取及校验当前证据。键包含身份授权指纹、KB集合、内容与ACL修订、规范query、filters、mode、top_k、上下文选项、generation以及模型/排序配置；启用scope或文档ACL时纳入相应状态。
- **实施与验收**：复用M3最终校验，重新构建上下文和关系证据；校验失败丢弃缓存并在deadline内重算，不返回旧响应或旧trace。首版不缓存超时/故障降级结果。验证撤权、删除、版本发布、关系变化和generation切换；比较开启前后的命中率、端到端P95、模型调用量及内存占用。
- **影响与依赖**：`services/retrieval.py`、配置与M4指标；进程内缓存不承诺跨副本共享命中率。只有测量证明需要共享缓存时再评审介质。

### C07 外部平台连接器

- **现状与场景**：当前只有文件/文本导入，尚无持续同步。连接器要解决外部文档ID、修订、删除和权限变化，不能仅实现定时抓取正文。
- **需要确认**：首个平台、空间/目录范围、只读同步还是双向写回、认证授权、同步时限、增量接口、删除信号、发布是否需人工审核，以及源权限能否准确映射。
- **建议方案**：每次只接一个平台的单向只读同步，新增平台适配器，复用PG任务、租约、退避和现有入库/发布管线。持久化连接器配置、源ID到document_id映射、源修订和同步游标；幂等键至少区分连接器、源对象和修订，避免重复导入。
- **实施与验收**：先实现限定范围全量导入，再增量更新、删除/撤权及周期对账；游标只在本批结果持久化后推进。超时或分页失败不等于源已删除；无法确定权限时隐藏受影响内容并告警，不能公开导入。验证重放、乱序事件、分页中断、限流和权限变更；删除/撤权同步不等待内容审核。
- **影响与依赖**：Worker调度、PG映射与检查点、平台适配器、管理入口及运行指标。优先将相同源权限资料映射为独立KB；若需混合权限，依赖C05。撤权传播时限必须先约定，轮询不能承诺即时撤权。

### C08 数据保留与硬删除

- **现状与场景**：当前删除设置`deleted_at`、递增内容修订并写outbox清理索引；没有恢复API、原件硬删除或备份到期清除流程。软删除不等于已支持恢复，也不等于数据已物理清除。
- **需要确认**：恢复期、历史版本保留期、硬删除触发方式、备份保留期、审计保存范围、保留例外和恢复权限。具体天数由业务给定，本方案不擅自设定。
- **建议方案**：优先落定保留策略；复用Worker及PG持久任务实现“立即隐藏→保留期→可重试清理→完成记录”。分阶段处理原件、正文/块、关系证据、相关任务载荷及派生索引；明确活动与历史generation的清理范围。留下最小删除标识、时间与阶段结果，不在审计中保存被删正文。
- **实施与验收**：原件按摘要共享，物理删除前检查所有仍需保留的版本引用，并防止与新上传并发竞态。若提供恢复，先校验权限、原件和版本，再重建投影并显式发布。备份不能随在线硬删除承诺即时清除，应按确认的到期规则处理；恢复旧备份后须先重放受保护的删除记录再对外服务。
- **影响与依赖**：PG增量迁移、`worker.py`、存储删除能力、关系/generation清理、管理接口和备份手册。验收中断续跑、共享原件、恢复竞态、过期数据不可恢复及备份恢复后的不复活；应与C03一起明确存储保留规则。

### C09 高可用拓扑

- **现状与场景**：当前单机Compose不具备主机故障容错；多开API容器也不能解决PG、OpenSearch、原件和模型服务的单点故障。
- **需要确认**：可用性目标与统计周期、稳态/峰值QPS、语料规模和增长、并行导入量；RTO（最长恢复时间）、RPO（最多可接受的数据丢失时间）；主机/机房故障范围、硬件及运维预算。现有10万块、5 QPS稳态/10 QPS短时只是实验建议，不是已确认容量。
- **建议方案**：分三步实施：①先完成当前拓扑的真实启动、压测与PG/原件备份恢复；②出现应用容量需求时部署多个API及Worker，补齐共享原件、连接池总预算、任务租约和模型在线/入库资源隔离；③依据RTO/RPO设计PG故障切换、OpenSearch副本、流量入口与模型冗余。部署平台按运维能力选定，不预设Kubernetes。
- **实施与验收**：保留手动构建镜像、部署引用镜像的D14边界。用故障注入分别测API退出、Worker租约接管、PG切换、索引/模型故障、原件不可用及整机恢复；记录实际恢复时间、丢失数据范围、P95、错误与降级率。OpenSearch可重建不意味着重建期间满足可用性目标。
- **影响与依赖**：部署配置、数据库连接/迁移门禁、Worker、存储、模型服务与告警手册；依赖M4指标和容量数据，多主机需要C03或另行确认的共享存储。未完成实测前不承诺SLA或固定硬件达标。
