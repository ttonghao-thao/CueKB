# CueKB 架构决策

状态：v0.1方案已于2026-09-09获用户确认；M0、M1、M2、M3编码已完成，后续编码状态以任务板为准。

| 编号 | 决策 | 原因与边界 |
| --- | --- | --- |
| D01 | 名称CueKB，中文名称“线索知识库”，目录cuekb；支持中文、英语等多语言 | 表达由线索找到知识；2026-09-22更正原“中文线索知识库”的歧义：中文名称不表示仅支持中文，多语言是已确认的产品范围；工作名未核验商标 |
| D02 | 检索优先，回答生成独立 | 缩短证据返回时间，便于客服Agent复用；2026-09-22由D19进一步明确回答完全归外部系统 |
| D03 | PostgreSQL＋OpenSearch | 事务性权威数据与搜索投影职责清晰；接受两者最终一致，但最终返回必须校验 |
| D04 | BM25＋稠密向量＋RRF＋有限重排 | 兼顾术语、口语与问题相关性；通过消融评测验证收益 |
| D05 | BGE-M3与bge-reranker-v2-m3作为质量基线 | 公开可复现的多语言基线，不宣称最新最强或CPU必达标 |
| D06 | 首期图谱存PostgreSQL，限定一跳 | 支持确定性上下文和关系扩展，控制噪声与成本 |
| D07 | 独立Worker＋数据库任务和outbox事件 | 不引入额外消息服务；以租约、重试和幂等处理任务 |
| D08 | 首期知识库级ACL | 边界容易验证；不同可见范围拆知识库，暂不声称支持文档级ACL |
| D09 | 首期API和评测闭环；门户后置 | 2026-09-15用户确认启动首期门户后被D13替代 |
| D10 | 原始文件保留、派生索引可重建 | 减少解析/模型升级造成的数据不可恢复风险 |
| D11 | 核心技术栈一致，生产和个人独立部署 | 共享维护成本，不混用数据；模型配置不同仍须各自评测 |
| D12 | 不自动按访问次数修改知识真伪或覆盖原文 | 使用行为仅作诊断与候选排序信号，避免强化错误 |
| D13 | API服务内置首期静态管理门户 | 直接复用现有API Key、ACL和导入/检索接口，不增加独立前端运行时；范围含导入、任务、文档版本、原文、删除和检索验证 |
| D14 | 镜像构建与Compose部署分离（2026-09-17） | 由操作员手动构建带本地标签的API/Worker镜像；Compose仅引用本地镜像，部署脚本不执行构建 |
| D15 | 外部模型服务由系统管理员在门户配置（2026-09-17） | 配置以PostgreSQL为权威，API Key用独立密钥加密；未配置Embedding时服务可启动，导入/检索明确阻断；模型变更仍受索引一致性约束 |
| D16 | 应用镜像按运行角色安装依赖（2026-09-19） | API仅安装Web与迁移依赖，Worker仅安装解析依赖；Docling固定使用CPU版PyTorch，避免为不使用本地GPU推理的Worker携带CUDA运行库；最终runtime层不保留uv和下载缓存 |

| D17 | M3使用有界一跳和可追溯上下文（2026-09-21） | 关系由知识库管理员提供当前发布证据，不从相似度推断因果；每次读取尝试共享REPEATABLE READ并在新事务中最终复验，避免旧快照隐藏撤权 |
| D18 | generation由PG指针切换并使用维护锁（2026-09-21） | 模型和物理索引在同一PG事务更新，避免跨系统别名/模型切换不一致；重建期间暂停内容写入、查询继续，回退用旧配置重建当前数据；当前注册分块版本为structured-v1 |

| D19 | CueKB专注检索，生成式回答完全由外部系统决定并集成（2026-09-22） | 用户明确CueKB是被外部系统集成的知识库，目标是快速检索准确结果；为保持集成灵活性，不提供内置回答服务、回答API、生成式模型配置或门户问答。外部系统自主决定直接使用结果还是交给自己的LLM。此决策收紧D02并取代原C01可选回答计划；Embedding、Reranker、检索证据评估和管理门户范围不变 |
